## Worktree-based Git workflow

- When using worktrees for development, treat each task's worktree branch as the source of its changes and the unit of integration. Commit meaningful, coherent changes on that branch as work progresses instead of accumulating a long-lived uncommitted working tree. Aim for commits that can be understood and reverted independently where practical; do not include unrelated work.
- Format the owned changes before committing, using the repository's applicable formatter, and include the intended formatting in the same coherent commit. Account for formatters that touch child modules or run asynchronously: inspect the resulting diff and avoid changing or staging unrelated work. Do not leave formatting changes to appear unexpectedly after the commit.
- Integrate completed work through Git branch history, normally by merging the worktree branch into its intended integration branch with a merge commit (`git merge --no-ff`). This preserves both the task boundary and its individual commits for inspection or targeted reversal. Follow repository-specific history rules or an explicit user instruction when they specify another approach.
- Snapshots and patches may support testing or review, but do not substitute copying their files directly into the integration branch for the normal worktree-branch merge. If a worktree contains mixed or unfinished changes, preserve them and organize the intended changes into appropriate branch commits rather than silently abandoning the branch history.
- Respect existing ownership, verification, push, deployment, destructive-operation and cleanup boundaries. Do not turn this workflow into unnecessary approval questions for ordinary work.

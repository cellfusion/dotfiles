## spec の基準

spec に入れるものは次の 7 つである。

- 目的 — 何のために作るかを書く
- 非目標 — 今回やらないと決めたことを書く。読み手が期待しうるもののうち、範囲外のものを挙げる
- 採用設計 — 何をどう作るかを書く。アーキテクチャ、コンポーネント、データフロー、エラー処理、テストを扱う
- 代替案 — 検討して採らなかった案と、採らなかった理由を書く
- 制約 — 守らなければならない前提を書く。バージョンの下限、依存の制限、命名や文言の規則、プラットフォームの要件が当たる
- 受け入れ条件 — 何が満たされたら完成かを、1 件ずつ確認できる形で書く
- 未解決事項 — 決まっていないことと、何をどう調べれば決まるかを書く

日付はその日の実際の日付を使う。「今日」「先週」のような相対表現を書かない。

## spec の self-review

書き終えたら新しい目で見直す。

1. **placeholder 走査** — 「TBD」「TODO」、書きかけの節、曖昧な要件が残っていないか。あれば直す
2. **内部整合** — 節どうしが矛盾していないか。アーキテクチャの記述と機能の記述が食い違っていないか
3. **スコープ** — 単一の実装プランに収まるか。収まらないなら分解が要る
4. **曖昧さ** — 2 通りに読める要件がないか。あれば片方に決めて明記する

見つけたその場で直す。再レビューは不要である。

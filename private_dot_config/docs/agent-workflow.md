# 開発エージェントの進め方

**明確な小変更は、現在のセッションで実装して確認する。** 進め方・仕様・原因のいずれかが不明なときだけ、対応するスキルを選ぶ。すべての作業を設計、計画、委譲、レビューの順に通す必要はない。

## 依頼から最初の手順を選ぶ

| 依頼・状況 | 選ぶ手順 | 避けること |
|---|---|---|
| 「この既存の表示文言を直して」 | 直接修正し、影響箇所を確認する | 設計承認や新規 worktree を既定にする |
| 要件は明確だが作業の分け方が不明 | `task-routing`。実行担当、別セッションの要否、書き込み先をそれぞれ判断する | 委譲、別タブ、別 worktree を一緒に選ぶ |
| 「ブレストしたい」「案を比較したい」、または動作や仕様に重要な選択肢が残る | `brainstorming`。影響の大きい選択だけ確認する。重要な設計案は `design-checkpoint-review`、長く残る判断は `architecture-decision-records` | 実装時に確かめられる細部まで事前に決める |
| 仕様は決まったが、依存関係や検証を伴う複数段階の実装が必要 | `writing-plans`。小さな既存計画は `executing-plans`、独立した実装・審査が必要な場合は `multi-agent-development` | 計画があるだけで並列化する |
| 不具合の原因が不明 | `systematic-debugging`。挙動を変える修正で有効なテスト境界があれば `test-driven-development` | 十分な根拠が揃った後も再現や調査を続ける |
| 「原因・選択肢を調べて教えて」 | 会話内で報告する。Vault に残す・Vault の既存ノートを探す場合だけ `research`（または明示呼び出し） | 単にスキルが読み込まれただけで Vault を更新する |
| 比較条件を固定して実験し、再利用できる記事にしたい | `experiment-to-article` | 実装中の小さな確認や、実装後に検証できる疑問をすべて実験にする |
| 委譲や別の会話が必要 | 実行中の環境の委譲手段を使う。別会話との通信は `agent-communication`、書き込みを分離するときは `using-git-worktrees`。Core の実行・通信は `herdr-core`、見た目の操作は `herdr-app` | 子の完了通知だけで成功とする。実行のためだけに表示やフォーカスを変える |
| 手元の差分を見てほしい／修正後に独立レビューがほしい | 軽い読み取りは `role-review`（配布後の明示呼び出し）、固定した差分の独立レビューは `requesting-code-review`、指摘の採否判断は `receiving-code-review` | 単なる読み取りレビューで修正や投稿を始める |
| GitHub PR をレビューしてほしい | 隔離して対象と確認範囲を記録するなら `pr-review`。checkout せず会話内で静的レビューする `pr-review-lite` は配布・動作確認後に利用する | 静的レビューで試験実行済みと報告する。依頼なしに投稿する |
| PR の作成や文面の準備／技術文書のレビュー | PR 準備は `create-pr`、文章の読みやすさや説明は `technical-writing-review`。日本語表現そのものが対象なら `natural-japanese` | 差分の正しさのレビューと文章のレビューを混同する |
| 完了を報告する／ブランチを統合する | `verification-before-completion` で主張に対応する証拠を確認する。統合・push・片付けは依頼がある場合だけ `finishing-a-development-branch` | 同じ状態で得た証拠を理由なく取り直す。完了報告を統合の許可とみなす |

`role-*` は作業の役割を明示するための定義で、自動的に別プロセスを作る仕組みでも、ツール権限を制限する仕組みでもない。`role-security-review`、`role-plan-auditor`、`role-implement`、`role-debug`、`role-research`、`role-question`、`role-ui` も該当する担当にだけ指定する。

| セッション履歴 | 11/12 UTC 以降に更新された通常の Pi・OMP のログから、今回の作業を除く直近の各30件を抽出。検証コマンドらしい記録は Pi 16件、OMP 7件。そのうち検証スキルへのパス参照が見えたのは Pi 13件、OMP 0件 | 読み込まずに検証した可能性や、ツールの記録形式差がある。未発動率とはみなさない。調査した Claude Code・Codex の履歴ディレクトリには同期間のログがなく、比較できない |
| 明示呼び出しと改修の試験 | Pi で `experiment-to-article` の展開記録を3件確認。`role-review` と `pr-review-lite` は定義があるが、今回確認した配布先では未配置 | 実験の試行と採用、ソースの定義と配布済み動作を別々に判定する。新しい役割・PR 経路は配布後に Rex 上で確認する |
| 監査ログ | 11/12〜11/19 UTC の開始記録は `verification-before-completion` 45件、`technical-writing-review` 60件、`task-routing` 1件。検証の開始・終端が対応する実行は45件、終端だけの実行は24件 | 終端の有無と、依頼どおりの実行・成功は別。文書レビューの件数は独立レビュー3件の完了を示さない。短い文面にも毎回3件委譲する現行条件は、費用・所要時間と指摘の有用性を比べてから変更する |

セッションでは明示呼び出しの展開、スキルパス、検証コマンド候補だけを確認した。パスの出現は本文を正常に読み終えた証拠ではなく、直近順の抽出も利用全体を代表しない。履歴本文はこの文書・集計出力には含めていない。

## 再点検する方法

監査イベントだけをローカルで集計する。コマンドは履歴本文を読まず、監査ログにも書き込まない。

```sh
agent-skill-audit --since 2026-11-12 --until 2026-11-20
```

適用前はリポジトリから `python3 private_dot_local/bin/executable_agent-skill-audit` で実行できる。`--since` は開始日を含み、`--until` は終了日を含まない（UTC）。同じ期間のスキル名・実行 ID で集計する。`paired_runs` は開始と終端（`finished`・`completed`・`blocked`）の両方が記録された件数で、成功数ではない。`start_only_runs`・`end_only_runs` には期間をまたいだ実行も含まれる。日付不明の行は期間に割り当てられないため、`ignored.invalid_json_or_date` に期間外の分も含まれる。

ブレストの自動選択を確かめるときは、ケースごとに Pi の新規セッションを使う。先に明示コマンドで読み込むと自動選択の確認にならない。

| 入力例 | 期待する動作 |
|---|---|
| 「通知の頻度について案を比較して。実装はしないで」 | `brainstorming` 本文を読み、選択肢を比較する。製品コードは変えない |
| 「既存の保存ボタンの文言を『保存する』に変えて」 | `brainstorming` を読まず、対応箇所を修正して確認する |
| 「保存するたびに通知が二重に出る。原因を調べて」 | `systematic-debugging` で原因を調べる。症状だけで設計の議論を始めない |

自動選択が見えない場合は、別の新規セッションで `/skill:brainstorming` を試し、スキルの認識と自動選択の問題を切り分ける。監査イベントがない場合は、本文を読み込んだツール結果も確認する。

適用後は、新規セッションで「小変更」「原因不明の不具合」「保存を指定しない調査」「Vault に残す調査」「既存の小さな計画」「独立レビューが必要な差分」を試す。期待したスキルが選ばれるかだけでなく、不要なスキル・書き込み・別セッションが発生しないか、必要な検証が実際に行われるかも確認する。結果は依頼の分類、実行環境、期待／実際の経路、検証の有無だけを残し、会話本文は転記しない。
